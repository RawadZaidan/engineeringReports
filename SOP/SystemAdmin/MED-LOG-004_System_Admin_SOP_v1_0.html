About This Document

This SOP defines how the System Administrator manages users, permissions, and core data records through the Django Administration Panel of the MEDILab internal platform. It covers four primary tasks: navigating the admin dashboard, managing user accounts (create, edit, deactivate), resetting passwords, and correcting trip/driver request records when errors occur.

This document is strictly for personnel with Superuser or Staff access to the Django admin panel. It is not for end users, requestors, drivers, or Logistics Handlers — those roles are covered in MED-LOG-001 through MED-LOG-003.

Actions performed in the admin panel take immediate effect across the entire system. There is no confirmation dialog for most operations. Proceed carefully and always verify changes after saving.

01Purpose
Purpose Statement This SOP establishes standardised procedures for the System Administrator to manage the MEDILab platform's backend through the Django admin interface. It ensures user accounts are created correctly, permissions are assigned consistently, passwords are reset securely, and trip request records can be corrected when errors are reported by the Logistics Handler or end users.
02Scope

Applies to: Any person granted Superuser or Staff access to the Django admin panel at /admin/. Typically the lead developer or designated IT administrator.

Covers:

  • Navigating the Django admin dashboard and understanding the CORE data models
  • Creating and editing user accounts (Authentication & Authorization → Users)
  • Assigning and modifying user permissions (Active, Staff status, Superuser status)
  • Resetting user passwords via the admin panel
  • Correcting driver request records when a Logistics Handler or requestor reports a data error

Does NOT cover:

  • Database-level operations (migrations, direct SQL queries, backups)
  • Server configuration or deployment procedures
  • Day-to-day trip scheduling — handled in MED-LOG-003
  • Adding new destinations, vehicles, or system configuration — handled in a separate configuration SOP
03Definitions & Abbreviations
TermDefinition
Django AdminThe built-in backend management interface of the Django web framework, accessible at /admin/. Allows direct CRUD operations on all database models registered in the admin.
SuperuserA user account with all permissions across the entire system without restriction. Can access and modify any record. Should only be assigned to the System Administrator.
Staff StatusAllows a user to log into the admin panel but with limited access — only to the models and actions explicitly permitted by their assigned permissions or group.
Active (checkbox)Controls whether a user account is enabled. Unchecking Active disables the account without deleting it — the correct way to offboard a user.
CORE (admin section)The data section of the admin panel containing MEDILab's operational models: Driver requests, Drivers, Engineers, Equipment Registry, Maintenance assignments/requests, Products, Reports, etc.
Driver RequestThe backend model corresponding to a trip request submitted through the Operational Logistics frontend. Can be edited directly in admin when the frontend doesn't permit a correction.
PBKDF2Password hashing algorithm used by Django. Passwords are never stored in plain text — the admin only shows the hash. Use "Reset password" to change a password.

06Procedure
PHASE ANavigating the Django Admin Dashboard
1
Access the admin panel and confirm you are logged in as the correct user. System Administrator
Navigate to the platform's /admin/ URL. The header of the Django admin panel displays "WELCOME, [YOUR USERNAME]" in the top-right corner. Verify this shows your account before taking any action.

If you are logged in as the wrong user, click Log out in the top-right, then log back in with the correct superuser credentials. Never perform admin actions under another person's account.

2
Orient yourself using the two admin sections: Authentication & Authorization and CORE. System Administrator
The Site Administration dashboard is divided into two functional sections. Understand which section handles each type of task before navigating.
AUTHENTICATION AND AUTHORIZATION
Groups+ Add✎ Change
Users+ Add✎ Change
CORE
Driver requests+ Add✎ Change
Drivers+ Add✎ Change
Engineers+ Add✎ Change
Equipment Registry+ Add✎ Change
Maintenance assignments+ Add✎ Change
Maintenance requests+ Add✎ Change
Products / Report images / Report items / Saved filters / Service reports+ Add✎ Change

Rule: All user account and permission tasks → Authentication and Authorization → Users. All trip/driver/maintenance data corrections → CORE → Driver requests (or the relevant model). Never use CORE to manage login access, and never use Authentication to edit operational data.

3
Use the Recent Actions panel to audit your own recent changes. System Administrator
The right column of the dashboard shows Recent Actions → My actions, listing your last admin operations with the record name, type (User, Driver, Engineer, etc.), and whether it was an addition or edit. Use this as a quick self-audit after any session.

If a recent action looks incorrect (wrong record modified), click it immediately to navigate to that record and verify. Do not wait until a user reports a problem.

PHASE BCreating or Editing a User Account
⚠️
Authorisation required before creating accounts with elevated permissions. Creating a standard user (Active only) does not require prior approval. Creating a Staff or Superuser account requires written authorisation from the General Manager before proceeding.
4
Navigate to Authentication and Authorization → Users → Add User (for new accounts) or click an existing username to edit. System Administrator
For a new user, click + Add next to Users. For an existing user, click ✎ Change to see the full user list, then click the username to open the change form. The Change User form contains three sections: credentials (username/password), personal info, and permissions.
5
Set or verify the username in the Credentials section. System Administrator
The username field accepts up to 150 characters: letters, digits, and @/./+/-/_ only. Use a consistent naming convention across all MEDILab accounts.

Recommended naming convention: Use the person's role identifier as the username for operational accounts (e.g., User, Sales, Procurement). For admin/engineer accounts, use FirstnameLastname format (e.g., RawadZeidan).

Usernames are case-sensitive in login. Inform the user of the exact capitalisation used.

6
Fill in Personal Info: First name, Last name, and Email address. System Administrator
These fields are optional in Django but should be completed for all real user accounts. They appear in audit logs and make it easier to identify accounts. For shared/role-based accounts (e.g., "User" or "Sales"), leave these blank or use the department name.
7
Set the correct Permissions for the account using the three checkboxes. System Administrator
The Permissions section contains three checkboxes. Assign exactly the level needed — do not over-provision.
Active
Designates whether this user account is enabled. All accounts must have this checked to allow login. Uncheck to disable an account without deleting it (e.g., when a staff member leaves).
✓ Check for all active accounts
Staff status
Allows this user to log into the admin site. Assign only to personnel who need backend access: IT staff, engineers managing equipment records, or designated deputies.
⚠ Requires General Manager authorisation
Superuser status
Grants all permissions across the entire system without restriction. This user can read, write, and delete any record in any model. Should be limited to the System Administrator only.
🚨 Assign to one person maximum. Requires GM authorisation.
🔀 Permission Assignment Decision
Standard user (requestor, logistics handler): Active ✓ only. Staff and Superuser unchecked.
Admin staff (IT, engineer with backend access): Active ✓ + Staff ✓. Superuser unchecked.
Superuser: Active ✓ + Superuser ✓. Assign only to System Administrator. Maximum one account.
8
Save the user record and verify the account appears correctly in the Users list. System Administrator
Click SAVE at the bottom of the form. The system will return you to the Users list. Locate the new or edited account and confirm the username, staff status badge, and active status are displayed correctly.

For new accounts, the user cannot log in until you set an initial password (see Phase C, Step 9). Inform the user of their username and direct them to contact you for their initial password — do not send passwords via unencrypted channels.

PHASE CResetting a User Password
ℹ️
Passwords are never stored in plain text. The admin shows only the hashing algorithm, iterations, and salt (e.g., algorithm: pbkdf2_sha256 iterations: 1200000 salt: e31O5u…). You cannot read the existing password — you can only replace it using the Reset Password function.
9
Open the target user's Change User form via Authentication and Authorization → Users. System Administrator
Locate the user by their username in the Users list. Click the username to open their Change User form. You will see the Password field displaying the hashed value — this is read-only and cannot be typed into.
10
Click Reset password directly below the hashed password display. System Administrator
The Reset Password button opens a separate form where you can set a new password for the user. This is the only supported method — do not attempt to edit the hash field directly.

The reset form will ask you to enter the new password twice to confirm. Django enforces password strength validation — the new password must not be too short, too common, or entirely numeric (unless the system's password policies have been customised).

11
Enter and confirm the new password, then save. System Administrator
Type the new password in both fields. If the passwords do not match, the form will reject the save and highlight the error. Click CHANGE PASSWORD to confirm.

After saving: The user's existing session (if any) is invalidated immediately — they will be logged out and must log back in with the new password.

Communication: Deliver the new password to the user through a secure channel (in person, phone call, or a password manager link). Do not send passwords via SMS or unencrypted chat.

Instruct the user to change their password after their first login if the reset was triggered by a security concern.

🚨
Never reset a password without a verified request. A password reset request must come from the user themselves or their direct manager — not from a third party claiming to act on their behalf. Verify identity before proceeding, especially for accounts with Staff or Superuser status.
PHASE DCorrecting a Driver Request Record
⚠️
This is a backend override. Editing a Driver Request directly in the admin bypasses the normal approval workflow. Only use this path when: (1) the Logistics Handler confirms the error cannot be corrected through the frontend Edit function, and (2) the correction has been communicated and agreed upon with the original requestor.
12
Obtain the exact TR number and field correction details from the Logistics Handler or requestor in writing. System Administrator
Before touching any record, ensure you have: the TR reference number (e.g., TR-0057), the specific field(s) that are wrong, and the confirmed correct value(s). Do not proceed based on verbal instructions alone.

Example correction request: "TR-0057 — Driver field shows Mohammad Abdallah but should be Samer Youssif. Date and time are correct. Requestor confirmed via WhatsApp at 10:32."

13
Navigate to CORE → Driver requests → Change and locate the record by TR number or date. System Administrator
From the Site Administration dashboard, click ✎ Change next to Driver requests in the CORE section. The list view shows all requests. Use the search bar or filter by date to find the specific record.
14
Click the record to open the Change Driver Request form and identify the fields to correct. System Administrator
The Change Driver Request form displays all editable fields for the trip record. Each field has inline action icons: ✎ edit (pencil, amber), + add (green), 👁 view (blue). Dropdown fields (Requester, Driver, Department, Destination) show the current value and can be changed via the selector.

Editable fields visible in this form:

  • Requester — the user account that submitted the request
  • Driver — the assigned driver account
  • Maintenance request — linked maintenance job (if any)
  • Department — originating department
  • Destination — the trip destination
  • Estimated distance — free text field (e.g., "30 km")
  • End User (Client) — free text
  • Contact person — free text
  • Contact number — free text

Note: Date, time window, and approval status fields may appear in different sections of the form — scroll down to locate them. Do not change the approval status field unless explicitly instructed.

15
Make only the confirmed corrections. Do not change any other fields. System Administrator
Change exactly the fields specified in the correction request. If a dropdown field needs to change (e.g., Driver), use the selector to choose the correct value. If a free text field needs updating, clear the old value and type the correct one.

For dropdown fields with the inline edit icon ✎: you can click the pencil to open the related record in a popup for detailed editing (e.g., opening a Driver profile). Only do this if the correction requires editing the related object — most corrections only require selecting a different dropdown value.

16
Save the corrected record and confirm the change is reflected. System Administrator
Click SAVE at the bottom of the form. The system will return you to the Driver requests list. Click the record again to verify the corrected values are saved correctly.

After saving, notify the Logistics Handler that the correction is complete. The Logistics Handler is then responsible for notifying the requestor (as per MED-LOG-003, Phase D). You are not responsible for end-user communication — your obligation ends at the Logistics Handler.

08Non-Conformance & Exception Handling
SituationActionEscalation
User cannot log in despite Active being checked Verify username capitalisation. Check if the account's password was ever set (new accounts have unusable passwords by default until reset). Perform a password reset (Phase C). If issue persists after reset, escalate to developer — possible session or server issue.
Request to deactivate a user account (staff departure) Uncheck Active on the user's Change User form and save. Do not delete the account — deletion removes audit history. Confirm with General Manager first. General Manager authorisation required before deactivation.
Correction request lacks written confirmation from requestor Do not proceed. Return the request to the Logistics Handler and ask them to obtain written requestor confirmation first. None — enforce the rule consistently.
Admin panel inaccessible (login fails, 500 error, or blank page) Do not attempt workarounds. Document the time and error message. Contact the hosting provider or developer immediately. Developer / hosting provider → General Manager if downtime exceeds 2 hours.
